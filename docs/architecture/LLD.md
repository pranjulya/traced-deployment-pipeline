# Low-level design
Status: ACCEPTED_AT_G0 (2026-09-25); paths below describe future implementation, not existing code.

## Interfaces
POST /v1/runs accepts bounded text (proposed 8 KiB UTF-8), required idempotency key for execution, and server-selected task type; returns run_id, status, sanitized answer and correlation ID. Reject malformed/oversized input before provider calls. No arbitrary tool or endpoint parameters. GET /health/live reports process health; /health/ready requires ledger writability and configuration validity, but telemetry unavailability does not fail readiness. Metrics endpoint is internal only.

Provider interface takes bounded messages, timeout and server-selected model and returns result, input/output token counts if known, provider_request_id if available, and typed error. Tool interface permits lookup of a fixture key only. One process enforces max concurrency 10 and returns 429 above capacity. A shared 30 s deadline bounds retries and tools. Retry at most twice for documented transient errors with jitter; never retry authentication/schema errors. Every actual provider attempt is separately accounted, including retried attempts.

## Ledger schema and lifecycle
usage_attempt: attempt_id primary key; run_id; ordinal; provider/model revision; started_at; ended_at; status (pending/completed/failed/unknown); token counts nullable; usage_origin (provider/estimated/unknown); price_version nullable; currency; decimal charge nullable; charge_state (observed/estimated/unknown/reconciled). Uniqueness on run_id + ordinal prevents duplicate completion writes. Prices use exact decimal arithmetic or integer minor micro-units, not floats. Store no prompt or output. Reconciliation adds an audit record and preserves original observations.

Commit pending before external dispatch. If commit fails, do not dispatch. Commit completion transactionally; if it fails after a response, return explicit accounting failure and leave the attempt pending/unknown for recovery. On restart, unresolved dispatched attempts become unknown, never zero. Run registry and admission are defined below. No promise of exactly-once provider execution or billing across crashes.

## Authentication and durable run admission
Use one injected application API secret in V1, mapped by trusted server configuration to a fixed principal alias such as demo-operator. Compare secrets safely; do not log headers. Provider credentials remain server-only and are distinct from the client credential. The client cannot supply or override its principal alias. Private/loopback deployment is default; TLS is required beyond loopback.

POST /v1/runs requires Idempotency-Key: 16–128 ASCII characters from a documented opaque-token alphabet. Missing or invalid key returns 400 before dispatch. Clients generate a new key for each intentionally new operation. Store an HMAC digest scoped to principal alias plus key, never the raw key; the dedicated HMAC secret is injected and persisted across ordinary restarts. Losing or rotating it while active registry entries exist risks bypassing duplicate detection, so rotation requires draining, preserving old-key lookup for the remaining retention window, and a reviewed migration.

run_registry: run_id primary key; principal_alias; key_digest; admitted_at; expires_at; state (accepted/running/completed/failed/accounting_unknown); safe_outcome_code; completed_at nullable. A unique constraint on (principal_alias, key_digest) and a single atomic admission transaction prevent concurrent duplicate execution. Only the transaction winner may dispatch. A conflict reads existing safe metadata and returns 409 with run_id, state, expires_at and fixed DUPLICATE_REQUEST code; it never redispatches or replays an answer. The request body of a duplicate is ignored after schema/size validation, even if different; no body digest or content is retained, and this semantic is explicitly documented to clients. The execution response is returned once; losing it requires inspecting metadata, not retrying for an answer.

Retain terminal entries for at least 24 hours from admission. Active or uncertain entries must not be deleted merely because 24 hours elapsed; first resolve/reconcile or administratively close with an audit reason. Expired terminal entries may be removed transactionally during admission/maintenance; after removal, reuse of the same key is a fresh execution and may incur new charges. There is no permanent deduplication guarantee. A crash after admission before dispatch is conservatively marked accounting_unknown on startup unless durable state proves no dispatch; do not automatically replay it. Apply a bounded registry capacity with admission rejection (503) when safe retention prevents pruning, rather than evicting unresolved keys.

## Post-result accounting failure
If provider output arrives but completion ledger commit fails, withhold the answer and return 503 with fixed ACCOUNTING_UNAVAILABLE and run_id. Do not issue another provider call. Best-effort update run_registry to accounting_unknown; if the database is unavailable, the durable pending attempt and active registry entry already preserve uncertainty, and startup recovery classifies them before new billable work. After ledger access recovers, retry of the same key returns 409 metadata, never a new dispatch; while storage is unavailable, return 503 without dispatch. Responding 503 does not imply the provider did not bill; run metadata and dashboard make that uncertainty explicit. Ledger writability failure makes readiness false and blocks further admission until recovery; telemetry availability is independent.

## Telemetry schema
Spans: agent.run → provider.attempt / tool.lookup; attributes allowlist includes operation, fixed provider/model aliases, attempt ordinal, status/error class, token counts when known, deployment revision. Correlation uses generated IDs only; incoming trace context accepted only at the trusted boundary or replaced. Metric labels: route template, operation, bounded outcome and configured model alias. Run/trace IDs, exception text and customer input are not labels. Disable automatic payload/header capture and sanitize exception events. Collector allowlisting is defense in depth after SDK-side minimization.

## Failure isolation and sampling
Start with 100% traces for low-volume fixtures, bounded SDK queues and export deadlines. A configurable head-sampling experiment compares 10% with 100%; no claim of retaining all errors under head sampling. Tail sampling is deferred until measured volume warrants its memory and routing complexity. Metrics and accounting remain unsampled. Telemetry export failures increment drop counters and do not block user requests. Ledger failure does block new billable work.
